## 1. 这个目录是什么

`knowledge/` 是 Agent 的知识来源。用户提问时，系统拿问题去检索这些条目，把命中的几条注入模型上下文，模型据此生成决策卡，并在 `knowledge_refs` 字段里指回具体的 `id`。

**为什么每条 `id` 必须写进上传版 md 的标题行**：`id` 只存在 JSON 字段里，模型看不到，就永远返回不了 `knowledge_refs`——「知识可溯源」这条防线会直接失效。所以 `build` 生成的 md 里，每条都是 `## [id] 标题` 的格式，不许改成纯标题。

## 3. 条目字段规范

```json
{
  "id": "laptop_004",
  "scope": "category",
  "category": "laptop",
  "keywords": ["笔记本", "校园特供", "开学季", "低色域"],
  "title": "校园特供机的三个缩水点",
  "content": "开学季线下渠道的「校园特供／学生专享」机型，常见缩水：屏幕从 100%sRGB 降到 45%NTSC、内存由双通道 8G×2 改单条 16G、硬盘由 PCIe4.0 降为 3.0。下单前拿型号到官网比对完整配置单。",
  "severity": "high",
  "updated_at": "2026-11-07"
}
```

| 字段 | 约束 | 最常见的错误 |
|---|---|---|
| `id` | `{域}_{三位序号}`，号段见 §4 | 插进已有号段中间 → 撞号，`knowledge_refs` 断链 |
| `scope` | `category` / `universal` | 横切条目写成 `category` → 只在某个品类下被召回 |
| `category` | `laptop` `digital` `chao_wan` `beauty` `bed` `study` `universal` | 写成中文或旧品类 `snack` `daily` → schema 判非法 |
| `keywords` | **3-6 个**，每个 ≤ 8 字，**至少 1 个用户会说的口语词** | 全是术语（「景品」「水口」「分模线」）→ 用户说「手办」就召回不到 |
| `title` | ≤ 16 字，是**规则名**不是话题名 | 「手办要注意什么」是话题，不是规则 |
| `content` | **60-120 字**，= 判断依据 + **具体动作** | 只描述现象不给动作（「注意辨别盗版」） |
| `severity` | `high`（会亏钱/伤身）/ `medium`（体验明显变差）/ `low`（优化建议） | 全标 high → 红线区块失去视觉权重 |
| `updated_at` | `YYYY-MM-DD` | 忘了更新 |

**内容红线**（违者整条重写）：

- 不写**具体型号**（写系列或档位），不写**精确价格**（写区间或折扣率）
- 不写「据说」「好像」「网友表示」——说不出依据就删
- 一条只讲**一个**规则，不要塞三个点
- 不写需要实时数据才能成立的内容（如「当前最低价」）
- 不出现 URL

## 4. 号段（**不许插号，只许追加**）

```
laptop_001-012      digital_001-012     chao_wan_001-012
beauty_001-012      bed_001-010         study_001-008
cross_001-018
──────────────────────────────────────
预留空号 21 个：013-015 / 013-015 / 013-015 /
                013-015 / 011-013 / 009-011 / 019-021
```

三条铁律：

1. **号段内允许空号**（写废了直接弃用，不补号、不重排）
2. **微增 1-2 条直接占用预留号**，不触发任何变更流程
3. **绝不能插进已有号段中间**——会撞号，历史 `knowledge_refs` 直接指错内容

`daily_`（日用品）与 `snack_`（零食）号段**已作废，不得复用**。

## 5. 校对五步法（每条都要过，五步全过才允许上传）

| 关 | 问自己 | 不过关怎么办 | 反例 |
|---|---|---|---|
| ① 事实关 | 这是**可验证的规则**还是我的印象？ | 说不清依据的，**整条删** | 「有些牌子品控不太行」→ 谁？哪批？删 |
| ② 时效关 | 有具体型号、精确价格、具体店铺吗？ | 改成系列 + 区间 | 「GSC 248 元」→「官方定价 6-7 折区间的现货」 |
| ③ 可执行关 | 读者知道**做哪个动作**吗？ | 补判断动作 | 「注意辨别盗版」→「翻盒底看镭射防伪贴，编号去官网查」 |
| ④ 归并关 | 和相邻条目讲的是同一件事吗？ | 合并，或换角度区分 | 003 和 008 都在讲「低价现货要警惕」→ 合并 |
| ⑤ 召回关 | `keywords` 里有用户真实会说的词吗？ | 补 1-2 个口语词 | `["景品","涂装","水口"]` → 补「手办」「正版」 |

**第 ① 关是答辩生死线**：评委问「这条依据呢」，要能当场回答「行业通识 / 平台规则 / 我自己踩过」。答不上来说明该删。

校对清单见 `docs/05_知识库_校对清单.md`（84 行，按人分工，可直接勾）。

### 5.1 单人执行时的校对动线（B 一人干完时用这条）

```
① python bikeng/tools/gen_review_sheet.py       生成 bikeng/review/校对单_日期.csv
② 双击用 WPS/Excel 打开，只在「结论」「修改意见」两列填字
③ python bikeng/tools/kb_apply.py --dry          先看会改什么，不写盘
④ python bikeng/tools/kb_apply.py                真正写入 JSON
⑤ python bikeng/tools/kb_build.py --lint         必须 PASS
⑥ python bikeng/tools/kb_build.py --md           生成上传版
⑦ 控制台上传 → 确认分段数 → 召回测试
```

结论列只认三个值：`OK`（保留）、`改`（用「修改意见」那格整段替换正文，须 60-120 字）、`删`（移出库，号段留空不补号）。空着 = 未审，保持原样。
**不要直接编辑 JSON**——84 条手改 JSON 迟早手滑少个逗号，而且改动没有记录。详细动线见 `docs/06_B岗_单人操作手册.md`。
表格存成 `.xlsx` 也能用（`kb_apply.py --file 路径.xlsx`，不依赖 openpyxl），CSV 存不进 WPS 时就走这条。

## 6. 校验与上传

```bash
# ① 结构校验（每次改完必跑）
node scripts/build-knowledge.js --in knowledge --out shared/build/knowledge.all.json --strict
# 期望：items: 84 / dup ids: 0 / schema errors: 0 / => PASS

# ② 生成上传版 md
node scripts/build-knowledge.js --in knowledge --out shared/build/knowledge.all.md --md
# 期望：84 个 "## [id] 标题" 分段
```

**A 的脚本还没就绪时**，用 `bikeng/tools/` 下的工具（等 A 的脚本上线后以 A 为准）：

```bash
python bikeng/tools/kb_build.py --lint    # 只校验磁盘 JSON，不动文件
python bikeng/tools/kb_build.py --md      # 校验通过后生成上传版 md
python bikeng/tools/kb_audit.py           # 内容体检：重复/无动作/召回模拟
```

> `kb_build.py --seed` 会用脚本内嵌初稿**覆盖** `knowledge/*.json`。除了“整体重置”，任何时候都不要跑它——内容已改为以 JSON 为准。

上传步骤（👤 人工，控制台操作）：

1. 云开发控制台 → AI+ → 知识库 → 新建「避坑知识库」
2. 上传 `shared/build/knowledge.all.md`（**不是 json**）
3. 等索引完成，状态变「已完成」，**确认分段数 = 84**
4. 在「决策 Agent」配置页勾选该知识库（**查证 Agent 不挂库**）

> 每次更新内容都要**重新上传并确认分段数**。只改本地 json 不重传，等于没改；旧条目还在库里被召回，会出现「明明删了却还在引用」。

## 7. 微增一条的完整动作（30 分钟）

| # | 动作 | 说明 |
|---|---|---|
| 1 | 占用预留号写条目 | 例：`beauty_013`，不改号段表、不改契约 |
| 1.5 | `python bikeng/tools/append_rows.py beauty_013` | 自动追加到校对单表尾（含行高与换行样式），结论列留空待审 |
| 2 | 跑 `--strict` | 必须 PASS |
| 3 | 重生成 md → 重传 → 确认分段数 | 84 → 85 |
| 4 | 补 1 条 Eval 用例 | 可选，但推荐 |

**加品类**才需要动 4 处（还要改 `CATEGORY` 枚举 + Agent prompt 品类清单）。漏了后两处的表现是「库里有内容但模型不用」——极难查，因为一切看起来都正常。

## 8. 常见错误（按踩坑概率排序）

| # | 错误 | 后果 |
|---|---|---|
| 1 | 改了本地 json 但没重新上传 | 模型用的还是旧内容，白改 |
| 2 | 上传了 json 而不是 md | 索引不到，`knowledge_refs` 永远为空 |
| 3 | 标题行去掉了 `[id]` | 模型无法引用条目，溯源能力归零 |
| 4 | 新条目插进号段中间 | 撞号，历史引用指错内容 |
| 5 | `keywords` 全是行业术语 | 用户口语提问召回不到 |
| 6 | 把「据说」类内容留着 | 答辩一戳就穿，连带削弱全库可信度 |
